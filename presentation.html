삽질의 기록 ①

카카오톡 인앱 브라우저 지옥

증상 팀원에게 카톡으로 링크 공유 → 카톡 내장 브라우저로 열림 → 마이크 권한창이 무한 반복으로 뜸. 인앱 브라우저는 권한을 기억하지 못한다.
해결 UA로 인앱 감지 → 경고 배너 + "크롬으로 열기" 원터치 버튼

삽질의 기록 ②

같은 말이 자꾸 길어지며 반복된다

받아쓰기: 잘못 쉴 → 잘못 쉴 때는 → 잘못 쉴 때는 무슨 일 → …
원인: 안드로이드 크롬이 확정 결과를 누적된 형태로 재전송

mergeFinal(base, add):
  add가 base로 시작하면 → 통째로 교체
  base 꼬리 == add 머리 → 겹친 만큼만 이어붙임
결과: "잘못 쉴 때는 무슨 일 하셨어요" ✓

1차 수정(재조립)은 실패 → 실제 중복 패턴을 시뮬레이션 테스트로 재현한 뒤에야 잡힘

프린터 미스터리

  • 도착한 프린터 이름이 SC05-A64B — 지원 목록에 없는 변종. 프로토콜 조사, 진단 로그, 방식 B 구현까지 준비했는데…

배운 것 — 기술

  • 데스크톱 성공은 아무것도 보장하지 않는다. Web Speech API 하나가 PC 크롬 / 안드로이드 크롬 / 카톡에서 전부 다르게 동작했다
  • 브라우저는 생각보다 멀리 간다. 앱 없이 카메라·캔버스 이미지 처리·BLE 프린터 제어까지. 단, iOS는 Web Bluetooth 불가 — "웹으로 되는가"보다 "우리 사용자 기기에서 되는가"
  • 공급망 조사도 개발이다. "페어링 시 블루투스 기기 이름이 뭔가요?" — 이 한 줄 질문이 시스템 성립 조건이었다

배운 것 — AI와 일하는 법

  • 자동화의 목표는 100%가 아니라 병목 제거. Suno 수동 30초를 남긴 덕에 비공식 API 리스크를 피했고, 그 30초는 품질 검수 지점이 됐다
  • 모든 자동 경로에 수동 폴백. 음성 인식이 죽어도 텍스트 입력으로, 프린터가 죽어도 PNG 저장으로 — 폴백 없는 자동화는 현장에서 죽는다
  • AI(Claude)와의 바이브코딩 — 스크린샷 던지고, 증상 말하고, 고친 파일 받아 커밋. 현장에서 문제 발견 → 당일 수정 배포가 실제로 됐다

인사이트

  • 지속가능성은 기술이 아니라 운영 설계다. 이 시스템의 성패는 프로토콜이 아니라 "사모님이 매주 충전하고 롤을 갈 수 있는가". 버튼 하나의 UI와 두 줄 매뉴얼이 코드만큼 중요한 산출물
  • 제약은 콘셉트로 뒤집을 수 있다. 흑백 디더링 → 옛날 신문 사진의 감성 · 바래는 감열지 → "평생 소장품"이 아니라 "매주 새로 받는 리추얼"
  • 제약을 먼저 수치화하고 역산하라. 60~90분 / 운영 1명 / 비개발자 20명 — 팀 코드, 질문 가이드, 원터치 복사가 전부 여기서 나왔다
